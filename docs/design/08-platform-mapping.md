# Spoolwarden design: platform mapping

This document specifies how one look (a theme, in Light or Dark) is produced on the web (the Hub page and the web
app) and in the Android app from one source, and how the two are kept equal. The tokens, the appearance switch, the
themes and their layout profiles are defined in `01-foundations.md`; this document does not repeat their values or
meaning, it says where each one goes and how it gets there.

## 1. Files and who owns them

One source per kind of thing. Everything else is generated from it by a script, and the generated files are checked
in, so nobody installing Spoolwarden runs a build step (foundations, section 12, rule 2). The token files live
together in one folder, `tokens/`, at the top of the repository, beside the code that is generated from them.
That folder is the only place they exist: the design folder holds no copy of `tokens.json`, `tokens.css` or the
two scripts, so there is nothing to keep in step. Values quoted in the design documents (foundations section 4,
`05-android-app.md` section 1) and the colours inside the mockups are illustrations of `tokens/tokens.json` at the
time of writing; where they differ, `tokens/tokens.json` is right for a value, and a change of the design starts
there (README, "Changing the design").

Every file in the table exists once the groundwork steps of `09-implementation-order.md` (stage 0) are in; the
"Status" column says which were there before them ("Exists") and which those steps added ("Proposed", specified
in section 3.4).

## 2. `tokens/tokens.json`

### 2.1 The file

`tokens/tokens.json` is the only source of every token value. Its shape is version 2. The top level holds two
keys, `version` and `themes`; everything else is inside a theme. A value is changed in this file and nowhere else,
and `build_tokens.py` is run afterwards (section 3.1).

### 2.2 Rules

- UTF-8 JSON. Formatting is free; the scripts read the file and never rewrite it.
- Every theme carries the same twelve keys: `label`, `profile`, `light`, `dark`, `type`, `space`, `radius`,
  `size`, `elevation`, `motion`, `derived`, `extra`. There is no inheritance between themes, so a reader sees a
  whole theme in one place. Only `extra` holds different keys per theme.
- Token keys are the token names of foundations section 4 **without** the leading `--` (`surface-2`,
  `accent-soft`, `fs-xl`, `r-s`, `t-fast`, `nav-mark`).
- Colours are written `#rrggbb` (upper or lower case). A colour with transparency is written `rgb(R G B / A)` or
  `rgba(R,G,B,A)`, with R, G, B integers from 0 to 255 and A a decimal from 0 to 1. The CSS carries each colour as
  written. A colour that `check_contrast.py` compares (every colour token except `scrim`) is opaque hex.
- Lengths are strings with their CSS unit: type sizes in `rem` (`"0.6875rem"`), every other length in `px`
  (`"4px"`), which become `dp` on Android. Durations are strings in `ms` (`"120ms"`). The easing is a
  `cubic-bezier(a, b, c, d)` string. Line heights and weights are strings holding a plain number (`"1.45"`,
  `"650"`); the CSS carries them unquoted.
- A key of `size` (or of `extra.size`) that ends in `-phone` is the value at 600 px and below of the key without
  the suffix: `ctl-phone` is `--ctl` on phones, Workbench's `extra.size.top-phone` is its `--top` on phones. It is
  emitted only where it differs from the base value (section 3.2).
- Elevation levels are CSS `box-shadow` values. A 1 px ring drawn with the shadow is written as the last part,
  `0 0 0 1px var(--<colour token>)`; the Kotlin output (section 3.4) reads the ring's colour token from it.
- Layout profile values must be one of the choices in foundations section 6.1.
- `derived` is documentation only and is never emitted. `extra` is emitted as custom properties; components must
  not use it (2.6).

### 2.6 The other three themes, `derived` and `extra`

The Workbench, Palette and Panes entries were transcribed from `mockups/a-workbench.html`, `mockups/b-palette.html` and
`mockups/d-panes.html`; each theme's `derived` list names the values that were not taken from its mockup (for
example the `size` entries a mockup has no equal for, copied from Console).

`extra` holds what a mockup has with no matching token: Console's `accent-2` gradient stop; Workbench's inverse
colours, hover tint, swatch line, card border, `lh` / `lh-tight`, `r-xl` / `r-full`, `top-phone` and the
`e1` / `e3` shadows; Palette's ring, toast and preview colours, `lh`, `fs-3xl`, `s8`, `r-pill`, `tap`, `btn-lg` and
`e1` / `e3`; Panes' knob and inverse colours.

`build_tokens.py` emits `extra` as custom properties: each group's extras follow that group's tokens in the same
block (`--accent-2` after `--code`, `--lh-tight` after `--fw-title`, `--e1` and `--e3` after `--e2`), and an
`extra.size` key ending in `-phone` goes into the phone block. Components must not use any of them: a component
reads only the tokens of foundations section 4 (the `size` entries included) and the names of 2.5, and proposed
test 4 (section 3.4) fails on any other name even though `tokens.css` declares it. A value a component needs that
only `extra` holds becomes a token first.

## 3. The generator and the equality test

### 3.1 The generator

`tokens/build_tokens.py` is a Python 3 script that uses the standard library only. It reads `tokens.json` in its
own folder and writes `tokens.css` beside it.

| Command | Does |
|---|---|
| `python tokens/build_tokens.py` | Writes `tokens.css` and prints its path and line count. |
| `python tokens/build_tokens.py --check` | Generates into memory and compares with `tokens.css` on disk. Exits 0 and prints `OK: tokens.css matches tokens.json` when they are equal; exits 1 with `FAIL: tokens.css differs from what tokens.json generates; run build_tokens.py` (or that the file does not exist) otherwise. Writes nothing. |

The output is deterministic: themes in file order; colours in the order of foundations section 4.1, and type, size
and motion keys in a fixed order, with any other key of those groups after them in alphabetical order; space,
radius, elevation and `extra` keys in file order; `\n` line endings, a final newline, no timestamps. Running it
twice in a row changes nothing the second time.

A developer who changes `tokens.json` runs the script and checks in `tokens.json` and `tokens.css` together in the
same change. The person installing Spoolwarden never runs it: the Hub serves the checked-in `tokens.css` as it is.

### 3.2 What `build_tokens.py` writes

**`tokens/tokens.css`**, one declaration per line, in this order:

1. The header line (section 1).
2. Each theme in file order, Console first:
   - a comment `/* <label> (nav: <nav>, collection: <collection>, detail: <detail>) */`;
   - the light block, on `:root` for Console and on `:root[data-look="<key>"]` for every other theme:
     `color-scheme: light`, the light colours, then type, space, radius, `size` (without the `-phone` keys), the
     light elevation and motion, each group followed by its `extra` entries;
   - the dark block, twice with the same declarations, as foundations section 5 requires: inside
     `@media (prefers-color-scheme: dark) { <light selector>:not([data-theme="light"]) { … } }` and under
     `<light selector>[data-theme="dark"] { … }`. A dark block holds only what changes with the appearance:
     `color-scheme: dark`, the dark colours and `extra.colour.dark`, and the dark elevation and
     `extra.elevation.dark`.
3. Phone: for each theme that has a `-phone` key whose value differs from its base, an
   `@media (max-width: 600px) { <light selector> { --<base>: <value>; } }` block. Today these are Console's
   `--ctl: 44px` and Workbench's `--top: 60px`.
4. Last: `@media (prefers-reduced-motion: reduce)` setting `--t-fast`, `--t` and `--t-slow` to `0ms` on `:root` and
   on each `:root[data-look="<key>"]`.

Which block wins:

| Competing blocks | Specificity | Decided by |
|---|---|---|
| Console's light (`:root`) against another theme's light (`:root[data-look="x"]`) | 0,1,0 against 0,2,0 | Specificity |
| A theme's light against its own dark blocks (`…:not([data-theme="light"])`, `…[data-theme="dark"]`) | 0,2,0 against 0,3,0 for a non-default theme; 0,1,0 against 0,2,0 for Console | Specificity |
| Console's dark against another theme's light | 0,2,0 against 0,2,0 | Nothing needs deciding for a token: wherever Console's dark block applies, the other theme's dark block (0,3,0) also applies and sets every colour and elevation token Console's dark block sets |
| A phone block against the light block of the same theme | Equal (0,1,0 or 0,2,0) | File order: the phone blocks come after every light block |
| The reduced-motion block against the light blocks | Equal | File order: it comes last |

An unknown or missing `data-look` falls through to Console. A property that only Console's `extra` defines
(`--accent-2`) stays visible under the other themes, which is one more reason components never use `extra`.

### 3.3 The checks

Two checks exist and run in the project's normal test run:

| Check | Command | Fails when |
|---|---|---|
| **`tokens.css` equals `tokens.json`** | `python tokens/build_tokens.py --check` | `tokens.css` was edited by hand, or `tokens.json` changed without running the script (exit 1, message as in 3.1). |
| **Contrast** (AUT-1 of `07-accessibility.md`) | `python tokens/check_contrast.py` (optionally with the path of a `tokens.json`) | For any theme in light or dark, a required pair is below its ratio. Required at 4.5:1: `text`, `muted`, `accent-text`, `ok`, `warn`, `bad`, `info` on `bg`, `surface` and `surface-2`; `ok`, `warn`, `bad`, `info` each on its `-soft` ground; `on-accent` on `accent`; `on-bad` on `bad`. Required at 3:1: `border-strong` and `focus` against `surface` and `bg`. It prints one table row per pair and exits 1 on a failure. `accent-text` on `accent-soft` and `text` on `surface-3` were advisory in the first version and are required since the check covers every pair of `07-accessibility.md` sections 3.1 and 3.2 (test 3 below). `ADJUSTMENTS.md` lists any colour changed to meet a ratio; the check writes no report file. |

The first check is the equality test of the web side today: a `tokens.css` that differs from its source cannot
pass.

### 3.4 Proposed additions to the token tooling

**Added by the groundwork steps.** Everything in this subsection is an addition this mapping needs beyond the first token files; `tokens.json`,
`build_tokens.py` and `check_contrast.py` do not do it today. Until the Kotlin output exists, the Android token
values are copied from `tokens.json` by hand into `SpoolwardenTokens.kt`, in the shape given below.

**Proposed keys in `tokens.json`.** Adding them raises `version` to 2.

`size.side-w` (`256px`, sidebar width; `--side-w`, `sizes.sideW`) and `size.list-w` (`360px`, section-pane width of the `list`
navigation; `--list-w`, `sizes.listW`) are already in `tokens.json`, `build_tokens.py` and `tokens.css`, in the `size`
group of every theme with the same values; they no longer sit in `extra.size`.

| Key | Console value | Purpose |

## 4. Token mapping

On Android the theme has two layers:

- **`SpoolwardenColors`**, a plain object with one field per colour token of foundations section 4.1, provided through the
  composition local `LocalSpoolwardenColors` and read as `SpoolwardenTheme.colors.<field>`. This is the full, one-to-one
  mirror of the web's custom properties. Every Spoolwarden composable reads its colours from here.
- **The Material 3 `ColorScheme`**, built from `SpoolwardenColors` by `SpoolwardenColors.toColorScheme()`. It exists so that the
  stock Material parts used inside the Spoolwarden composables (and anything Material draws on its own, such as
  the text cursor) come out in the theme's colours. Material has no slot for ok, warn, info, their soft grounds,
  focus, code, the third surface or the accent hover; those live only in `SpoolwardenColors`.

Rules:

- `inversePrimary` has no token of its own: it is the `accent-text` of the other appearance of the same theme.
- **Why `primary` is `accent-text`, not `accent`.** Material draws `primary` as content on surfaces: the label of
  a text button, a checked box, a switch that is on, a progress indicator, the cursor and the focused label of a
  field, the selected tab. A theme's `accent` may be too light for that (Palette light: 2.20:1 on `surface`), while
  `accent-text` is checked at 4.5:1 on `bg`, `surface` and `surface-2` in every theme. So every stock component is
  readable without being told its colours, and `onPrimary` is `surface`, which has the same ratio against it. Only
  the filled main button and the chosen segment take `accent` and `onAccent`, from `SpoolwardenColors`
  (`07-accessibility.md` CON-8 and CON-9).
- Any role the table does not name (for example the `…Fixed` roles of newer Material versions) is still set
  explicitly by `toColorScheme()`, never left at Material's baseline purple: container-like roles take
  `accentSoft`, their `on…` roles take `accentText`. A Spoolwarden composable never reads such a role.
- The secondary and tertiary roles repeat the accent because Spoolwarden has one accent. Stock parts that pick
  `secondaryContainer` for a selected state (segmented buttons, filter chips) therefore show `--accent-soft`,
  as the web does.
- Status meaning is never taken from `primary` or `tertiary`. A success line is `ok` on `okSoft`; a "revised by
  AI" note is `info` on `infoSoft` (the current app uses `primary` and `tertiaryContainer` for these, in
  `ui/spool/SpoolCard.kt` and `ui/add/ReviewScreen.kt`).
- Text selection: web `::selection { background: var(--accent-soft); color: var(--text); }`; Android
  `LocalTextSelectionColors provides TextSelectionColors(handleColor = accentText, backgroundColor = accentSoft)` (the handle is a mark on a surface, so it is `accentText`, not `accent`).
- Filament colours come from the data on both platforms (foundations section 4.1) and never pass through
  `SpoolwardenColors`.

## 6. Space, size, density, radius, elevation, motion

### 6.1 Space

`Spacing` is a plain object with the seven steps in dp (`Spacing(s1 = 4.dp, … s7 = 48.dp)` in Console), provided
by `LocalSpacing` and read as `SpoolwardenTheme.space.s4`. Paddings, gaps and margins on Android take only these
values, as on the web only `var(--s1)` … `var(--s7)` are used.

### 6.2 Control height, rows and hit areas

| Thing | Web | Android |
|---|---|---|
| Visible height of buttons, segmented controls, chips | `min-height: var(--ctl)`; `--ctl` is 40 px, 44 px at or below 600 px (Console) | `Modifier.height(SpoolwardenTheme.density.control)`; `control` resolves to `controlPhone` when the window class is Phone |
| Visible height of text fields | `min-height: var(--ctl)` | Material's `OutlinedTextField` height, which holds the floating label (section 10.4; section 14) |
| Hit area | A `::after` layer that extends the control to 44 px (foundations section 4.3) | `LocalMinimumInteractiveComponentSize` stays at Material's 48 dp; every Spoolwarden control applies `Modifier.minimumInteractiveComponentSize()`, so a 40 dp button is touchable over 48 dp |
| Collection item | `min-height: var(--row)` | A `ListItem` keeps its own minimum height (section 14); any other tappable row uses `heightIn(min = max(density.row, LocalMinimumInteractiveComponentSize.current))`; a row that cannot be tapped uses `density.row` |
| Space between separate items (cards, tiles, stacked rows on phones) | `gap: var(--gap)` | `Arrangement.spacedBy(density.gap)` |
| Hairline between table rows | `border-top: 1px solid var(--border)`, no gap | `HorizontalDivider(thickness = 1.dp, color = colors.border)`, no gap |

A theme changes density only through `ctl`, `ctl-phone`, `row` and `gap` (foundations section 4.3).

`SpoolwardenTheme.density` returns a `SwDensity`, built from the theme's `SwSizes` and the window class
(section 3.4). Both names avoid a bare `Density` because Compose already has a `Density` type for pixel conversion;
the "Density object" of foundations section 6.2 is `SwDensity`.

### 6.3 Radius

| Token | CSS | `Shapes` slot(s) | Direct |
|---|---|---|---|
| `--r-s` | `--r-s` | `extraSmall` | `SpoolwardenTheme.shapes.rS` |
| `--r` | `--r` | `small`, `medium` | `SpoolwardenTheme.shapes.r` |
| `--r-l` | `--r-l` | `large`, `extraLarge` | `SpoolwardenTheme.shapes.rL` |

Material components do not all read the slot their size suggests (Material buttons are fully rounded whatever
`Shapes` says; outlined text fields read `extraSmall`; dialogs read `extraLarge`). Therefore every Spoolwarden
composable passes its shape explicitly, as given in the component table (section 10), and never relies on a
Material default.

### 6.4 Elevation

| Level | Web | Android | Used by |
|---|---|---|---|
| `--e0` | `box-shadow: var(--e0)` (Console: `none`) plus the component's own 1 px `--border` | `Surface(shadowElevation = e0.dp)` (Console: 0 dp) plus `BorderStroke(1.dp, colors.border)` | Bars, cards, panels, tables, inputs, the job panel |
| `--e2` | `box-shadow: var(--e2)` (shadow and, where the theme has one, a 1 px ring: in Console `--border`, or `--border-strong` in dark) | `Modifier.shadow(e2.dp, shape)` (Console: 8 dp) and, where `ring` is set, `BorderStroke(1.dp, <ring colour>)` | Dialogs, sheets, menus and toasts only (foundations section 4.3) |

- **Tonal elevation is off in every theme.** Every `Surface`, card, sheet, dialog and menu is given
  `tonalElevation = 0.dp`, and `surfaceTint` equals `surface` (section 4.1), so no Material part tints itself
  with the accent when it rises. Things are told apart by hairlines and by `--surface` against `--bg`, exactly as
  on the web. In Console, `e0` is no shadow at all: hairlines only.
- Material components that carry their own default elevation (cards, menus, navigation bars) are given
  elevation 0 and the theme's `e0` or `e2` instead.

### 6.5 Motion

| Token | Web | Android | Used for |
|---|---|---|---|
| `--t-fast` | `transition: … var(--t-fast) var(--ease)` | `tween(motion.fast, easing = motion.easing)` | Hover, press, switch thumb |
| `--t` | `var(--t)` | `tween(motion.base, …)` | Menus, toasts, expanding rows, chevron turn |
| `--t-slow` | `var(--t-slow)` | `tween(motion.slow, …)` | Sheets, dialogs, side drawer |
| easing | `var(--ease)` | `motion.easing` | All of the above |

Reduced motion:

- Web: the last block of `tokens.css` sets the three durations to 0 ms under `prefers-reduced-motion: reduce`.
- Android: when the system setting "Remove animations" is on (`Settings.Global.ANIMATOR_DURATION_SCALE` is 0),
  `SpoolwardenTheme` provides a `SwMotion` with all three durations 0.
- On both, the spinner (`spinner`, `SwSpinner`) is replaced by the static label "Working…" while reduced motion is
  on, and progress bars jump to their new value.

## 7. Breakpoints and window classes

| Window class | Web | Android (`WindowClass`) |
|---|---|---|
| Phone | up to 600 px: `@media (max-width: 600px)` | compact width (below 600 dp) |
| Tablet | 601 to 1024 px: `@media (min-width: 601px) and (max-width: 1024px)` | medium width (600 to 839 dp) |
| Desktop | over 1024 px: `@media (min-width: 1025px)` | expanded width and any wider class (840 dp and up) |

- The web edges are the widths of foundations section 7 (600 and 1024 px); `build_tokens.py` writes the 600 px edge
  into its phone block. CSS media queries cannot read custom properties, so stylesheets write these two numbers
  literally; proposed test 4 of section 3.4 checks that every width in a media query of the web stylesheets is one
  of them (or one more).
- Android reads the window size class with `currentWindowAdaptiveInfo().windowSizeClass` (Material 3 adaptive), as
  foundations section 7 and `05-android-app.md` section 1 say, and maps it to `WindowClass`: compact to Phone, medium
  to Tablet, expanded and any wider class to Desktop. `WindowClass` is provided by `LocalWindowClass`. The class
  comes from the window, not the screen, so split screen and freeform windows get the layout their width calls for,
  and it is recomputed when the window changes size.
- The Android edges are therefore Material's (600 and 840 dp), not the web's 600 and 1024 px. A window from 840 to
  1024 wide is Desktop in the app and Tablet in a browser; section 14 lists this.
- The content column on Desktop is at most the 1400 px layout width of foundations section 7, held by the proposed
  `size.content-max` entry (section 3.4): `max-width: var(--content-max)` on the web,
  `Modifier.widthIn(max = SpoolwardenTheme.sizes.contentMax)` on Android. The side drawer's width on Desktop is
  `size.drawer` on both (`var(--drawer)`, `SpoolwardenTheme.sizes.drawer`).
- One CSS pixel is treated as one dp. On phones and tablets the two match closely; this is what lets one set of
  numbers serve both.

## 8. Appearance switch per platform

The choice, its default and where its controls sit are in foundations section 5. This section says how each
platform stores and applies it.

| | Web (Hub page and web app) | Android app |
|---|---|---|
| Stored where | `localStorage`, key `spoolwarden.appearance` | The app's settings store (DataStore, today `fk/data/Settings.kt`), key `appearance` |
| Values | `light`, `dark`, `system` | `light`, `dark`, `system` |
| Missing or unknown value | System | System |
| Applied by | `data-theme` on `<html>`: set to `light` or `dark`; removed for System | `SpoolwardenTheme(look, appearance)`: System uses `isSystemInDarkTheme()`; Light and Dark override it |
| Before the first paint | `tokens/theme-init.js` (below) | The app already reads its stored settings before drawing anything; the window background before that comes from `sw_window.xml` |
| When the system flips while System is chosen | The `prefers-color-scheme` media blocks follow at once; no script | `isSystemInDarkTheme()` recomposes |
| When the person changes it | Set or remove the attribute, write the key, update the status-bar colour (section 13). No reload. | Write the key; the theme recomposes. No restart and no activity recreation, because `MainActivity` handles the `uiMode` change itself (below). |
| Other open copies | A `storage` event applies the new value in other tabs | Not applicable |
| Storage unavailable (private browsing) | The choice applies to the open page only; every `localStorage` call is wrapped so it cannot throw | Not applicable |

**`tokens/theme-init.js`** is loaded as the first script in `<head>`, after the `charset` and `viewport` metas and
before the first stylesheet, with a plain `<script src>` (not `defer`, not `async`), so the attributes are set
before anything paints. It is a file, not an inline script, because the Content-Security-Policy forbids inline
script (foundations section 12). It is a proposed output of `build_tokens.py` (section 3.4), so that the list of
theme keys always matches `tokens.json`:

```js
// Spoolwarden design tokens. GENERATED by build_tokens.py from tokens.json. Do not edit by hand.
(function (r) {
  var a = null, l = null;
  try { a = localStorage.getItem("spoolwarden.appearance"); l = localStorage.getItem("spoolwarden.look"); } catch (e) {}
  if (a === "light" || a === "dark") r.setAttribute("data-theme", a);
  if (["console", "workbench", "palette", "panes"].indexOf(l) >= 0) r.setAttribute("data-look", l);
})(document.documentElement);
```

**Android specifics.**

- **No dynamic colour.** `dynamicLightColorScheme` and `dynamicDarkColorScheme` are never called. The phone's
  wallpaper never changes the look, so the app and the web pages show the same colours.
- **System bars follow the app, not the phone.** The app draws edge to edge (as today). Whenever the resolved
  appearance changes, the activity calls `enableEdgeToEdge` with `SystemBarStyle.dark(TRANSPARENT)` for Dark or
  `SystemBarStyle.light(TRANSPARENT, TRANSPARENT)` for Light, for both the status and the navigation bar, so the
  bar icons stay readable when the person picks Dark on a phone set to light (the current
  `SystemBarStyle.auto` follows the phone only).
- **The next launch starts right.** On Android 12 and newer the app calls
  `UiModeManager.setApplicationNightMode` (`MODE_NIGHT_NO`, `MODE_NIGHT_YES` or `MODE_NIGHT_AUTO`) whenever the
  choice changes, so the system's splash and the window background of the next launch use the chosen appearance.
  Android 10 and 11 have no such call; see section 14.
- **No recreation on a light/dark change.** The call above changes the app's `uiMode` configuration at once, and so
  does the phone's own light/dark switch. By default Android recreates the activity on a `uiMode` change, which would
  throw away what is being typed (foundations principle 4); today the manifest declares no `configChanges`.
  `MainActivity` therefore declares `android:configChanges="uiMode"` in `AndroidManifest.xml`: the activity stays,
  Compose receives the new configuration, `isSystemInDarkTheme()` returns the new value and the theme recomposes.
  With System chosen the app's night mode is `MODE_NIGHT_AUTO`, so `isSystemInDarkTheme()` still follows the phone.
  Check on a device: type into a field, choose Light, Dark and System in turn, switch the phone's dark theme, and
  confirm the typed text stays and `onCreate` does not run again.

## 9. Theme switch per platform

Which themes exist, what they are made of and where the picker sits are in foundations section 6.

| | Web | Android |
|---|---|---|
| Stored where | `localStorage`, key `spoolwarden.look` | The settings store, key `look` |
| Values | `console`, `workbench`, `palette`, `panes` | `console`, `workbench`, `palette`, `panes` (the `Look` enum) |
| A device that has not chosen | The `data-look` the Hub rendered on `<html>` (its default theme, section 15); if none, the CSS falls through to Console on bare `:root` | The Hub's default theme from `GET api/info` (section 15); if unknown, Console |
| Applied by | `data-look` on `<html>` | `SpoolwardenTheme(look, appearance)` |
| Token set | The theme's blocks in `tokens.css` (section 3.2) | `SpoolwardenTokens.of(look)` |
| Layout profile | CSS only (below) | Three composition locals: `LocalNavStyle`, `LocalCollectionStyle`, `LocalDetailStyle` |
| Changing | Set the attribute, write the key, update the status-bar colour. No reload. | Write the key; the theme recomposes. No restart. |

**Layout profile on the web.** The markup of navigation, collections and detail regions is the same in every
theme; the stylesheet arranges it. Rules for a profile choice are grouped in the component stylesheet under a
comment `/* profile: <profile key>=<choice> */`, and every selector in the group starts with the `data-look`
values of exactly the themes whose profile has that choice (today one theme each, for example
`:root[data-look="workbench"] .coll`). Rules for the default theme's choices are written without a
`data-look` qualifier, so an unknown look falls back to Console's arrangement as well as its tokens. Proposed test 4
of section 3.4 also checks each group's themes against `tokens.json`.

**Layout profile on Android.** The composables that arrange things (`SwNav`, `SwCollection`, `SwDetail`,
section 10) read the composition locals and pick their arrangement; screens never branch on `Look`. `SwNav` is one
`NavigationSuiteScaffold` whose `layoutType` it sets from `LocalNavStyle` and the window class: `NavigationBar` on
Phone; on Tablet and Desktop `NavigationRail` for rail, `NavigationDrawer` (Desktop) or `NavigationRail` (Tablet)
for sidebar, none with a `PrimaryScrollableTabRow` under the top bar for pills, and none with the list pane of
`ListDetailPaneScaffold` for list (section 10.1). `nav` applies at Tablet and Desktop only. On Phone, Console,
Workbench and Palette use the bottom bar, and Panes opens on its list of sections and drills in (foundations
section 6).

**`SpoolwardenTheme`.** Hand-written in `SpoolwardenTheme.kt`; the values come from the generated
`SpoolwardenTokens`.

```kotlin
enum class Look { Console, Workbench, Palette, Panes }
enum class Appearance { Light, Dark, System }
enum class WindowClass { Phone, Tablet, Desktop }

object SpoolwardenTheme {
    val colors: SpoolwardenColors @Composable @ReadOnlyComposable get() = LocalSpoolwardenColors.current
    val type: SwType @Composable @ReadOnlyComposable get() = LocalSwType.current
    val space: Spacing @Composable @ReadOnlyComposable get() = LocalSpacing.current
    val sizes: SwSizes @Composable @ReadOnlyComposable get() = LocalSwSizes.current
    val density: SwDensity @Composable @ReadOnlyComposable get() = LocalSwDensity.current
    val shapes: SwShapes @Composable @ReadOnlyComposable get() = LocalSwShapes.current
    val elevation: SwElevation @Composable @ReadOnlyComposable get() = LocalSwElevation.current
    val motion: SwMotion @Composable @ReadOnlyComposable get() = LocalSwMotion.current
    val window: WindowClass @Composable @ReadOnlyComposable get() = LocalWindowClass.current
}

@Composable
fun SpoolwardenTheme(look: Look, appearance: Appearance, content: @Composable () -> Unit) {
    val t = SpoolwardenTokens.of(look)
    val dark = when (appearance) {
        Appearance.Light -> false
        Appearance.Dark -> true
        Appearance.System -> isSystemInDarkTheme()
    }
    val colors = if (dark) t.dark else t.light
    val other = if (dark) t.light else t.dark
    val window = rememberWindowClass()          // from currentWindowAdaptiveInfo(), section 7
    val reduceMotion = rememberReduceMotion()   // section 6.5

    CompositionLocalProvider(
        LocalSpoolwardenColors provides colors,
        LocalSwType provides SwType(t.type, window),          // `input` depends on the window class
        LocalSpacing provides t.space,
        LocalSwSizes provides t.sizes,
        LocalSwDensity provides SwDensity(t.sizes, window),   // `control` depends on the window class
        LocalSwShapes provides SwShapes(t.radius),
        LocalSwElevation provides if (dark) t.elevationDark else t.elevationLight,
        LocalSwMotion provides if (reduceMotion) SwMotion.Off else t.motion,
        LocalWindowClass provides window,
        LocalNavStyle provides t.profile.nav,
        LocalCollectionStyle provides t.profile.collection,
        LocalDetailStyle provides t.profile.detail,
    ) {
        MaterialTheme(
            colorScheme = colors.toColorScheme(dark = dark, inversePrimary = other.accentText),
            typography = t.type.toTypography(),
            shapes = t.radius.toShapes(),
        ) {
            CompositionLocalProvider(
                LocalContentColor provides colors.text,
                LocalTextSelectionColors provides TextSelectionColors(colors.accent, colors.accentSoft),
                content = content,
            )
        }
    }
}
```

`toColorScheme()` sets every role of the Material version in use, following section 4.1. A JVM unit test in the
app (`ColorSchemeTest`, run by the normal Gradle unit-test task) builds the scheme for every theme in light and
dark and fails if any role holds a colour that is not one of that theme's `SpoolwardenColors` values (the opaque scrim and
`inversePrimary` excepted). This is what keeps Material's baseline colours out of the app.

The theme picker's preview tiles draw each theme with `SpoolwardenTokens.of(look)` and the current appearance,
not with the active theme, so every tile shows its own colours (foundations section 6.2). On the web the tile's
root carries its own `data-look` attribute and the proposed preview tile blocks of `tokens.css` (section 3.4) repeat
each theme's blocks keyed on `[data-look="<key>"]` without `:root`, so the tile's tokens apply inside the tile only.

## 12. Words

One string catalogue serves the web pages and the app, so the same thing is called the same everywhere
(foundations principles 5 and 6). The catalogue and its generated files are proposed additions to the tooling
(section 3.4).

**Source: `strings/en.json`.** A flat object, keys in lower snake case, grouped by a prefix for the place
(`printers_title`, `printer_forget`, `appearance_system`, `theme_console_line`). A value is a text, or for a
text that depends on a count an object `{ "one": "…", "other": "…" }`. Placeholders are written `{name}` in lower
snake case; `{count}` is the number a plural depends on.

```json
{
  "app_name": "Spoolwarden",
  "appearance_light": "Light",
  "appearance_dark": "Dark",
  "appearance_system": "System",
  "printer_forget": "Forget printer",
  "printer_forget_question": "Forget {printer}?",
  "command_name": "spoolwarden",
  "printer_forget_body_bambu": "{product} stops connecting to it and deletes its Access Code. To use it again, add it again.",
  "printer_forget_body_klipper": "{product} stops connecting to it and deletes its Moonraker API key, if one is saved.",
  "status_fix_run": "Run {command} status on the Hub.",
  "spools_added": { "one": "{count} spool added", "other": "{count} spools added" }
}
```

**The product's name is held once.** `app_name` is the only entry whose text contains the product's name, and
`command_name` the only one that contains the command's name. Every other text that names either uses the
reserved placeholders `{product}` and `{command}`; the generator fills them from those two entries, so they are
not arguments at run time: `strings.js` and `strings.xml` hold the finished text, and no caller passes the name.
The app's launcher label is `@string/app_name`; the web app manifest's `name` and `short_name` (section 13), the
top bar and the browser tab take the same entry. Where a part of this design writes "Spoolwarden" or
`spoolwarden` inside a text, it stands for these two entries. A change of the product's name is therefore a
change of two lines and a regeneration. Test 7 also fails when any other entry contains the value of `app_name`
or of `command_name` as a word. Addresses and identifiers that are not text on screen (the deep-link scheme,
storage keys, file and package names) are not part of the catalogue and do not follow these entries.

**Generated files.**

| | Web: `strings/strings.js` | Android: `res/values/strings.xml` |
|---|---|---|
| Form | `window.SW_TEXT = Object.freeze({ … })`, keys and texts as in the source | `<string name="key">…</string>`; plurals as `<plurals name="key">` with `<item quantity="one">` and `<item quantity="other">` |
| Placeholders | Kept as `{name}`; the shared page script's `t(key, values)` replaces them and picks the plural form with `Intl.PluralRules("en")` | Numbered in order of first appearance: `{count}` becomes `%n$d`, every other placeholder `%n$s`; a comment above the string lists the order (`<!-- 1=printer -->`); read with `stringResource` / `pluralStringResource` |
| Escaping | JSON string escaping | `'` and `"` escaped with a backslash, `&` and `<` as XML entities, a a leading `@` or `?` escaped, a backslash and a line break escaped, leading, trailing and double spaces kept by quoting. A literal `%` is written `%%` in a string that has placeholders; a string without placeholders keeps the bare `%` and is marked `formatted="false"`, because Android reads it without formatting |
| Loaded | With `<script src defer>` after `theme-init.js` | Bundled; it is the app's only string file, so every text the app shows, including the app's name, comes from it |

- Proposed test 7 of section 3.4 parses both generated files and compares them with the source: same keys, same
  texts after undoing the placeholder and escaping rules, same placeholder names per key. It also fails on any string literal
  containing a letter in the hand-written Kotlin under `ui/` (whatever parameter it is passed to: `text`, `label`,
  `contentDescription`, a `NoticeCard` message) and on such a literal given to `textContent`, `ariaLabel`, `title`,
  `placeholder`, `announce(` or `toast(` in the page scripts. Routes, keys, log tags and MIME types are listed in
  `tests/strings_allowlist.txt`, so text reaches the screen without the catalogue only through a reviewed entry
  there.
- Text that arrives from the Hub while running (a printer's name, a message about one specific failure) is shown as
  it arrives and is not in the catalogue.

**One key per meaning, one text per key.** Where two interfaces show the same thing they read the same key, so
no key carries an interface in its name (`_hub`, `_web`, `_app`). Two keys may hold the same text only when they
mean different things ("System" as the navigation group and "System" as the appearance choice); keys that mean the
same are merged (the status words are the `status_…` keys, used by every badge and chip).

**A label never carries its unit.** A field's label is the bare name ("Nozzle", "Net weight", "Density",
"Weight with spool"); the unit is shown inside the field (`02-components.md` section 5.4; the `suffix` of the text
field on Android) and comes from its own key (`unit_g`, `unit_c`, `unit_g_cm3`, `unit_mm3_s`, `unit_days`). In a
key-value list the unit follows the value ("1000 g", "210 °C"). "(optional)" stays in the label, alone in its
brackets. A format a person must type goes in the placeholder or the hint ("e.g. 190-220"; for a colour the hint key
`common_field_colour_hint`, "A hex colour, like #2B2B2E"), not in the label.

**Shared wording.** One term per thing, in every interface (Hub page, web app, app and the `spoolwarden` command)
and in the user documents. Each term is one catalogue key (`common_…` where several screens use it), so the interfaces
cannot drift apart; the words lint (`07-accessibility.md` AUT-7) lists the words in the right-hand column.

| Thing | Term | Never |
|---|---|---|
| What a spool weighs on a scale, filament and empty spool together | "Weight with spool" (also the field's label; the unit g is shown inside the field) | "Gross weight", "Weight on the scale", "scale weight" |
| Repeating a request that failed | "Try again" | "Retry" |
| Hint under an optional field that the Hub fills in by itself when it is left empty (location, Bambu Studio parent, density) | "Leave empty to choose automatically." | "Blank = automatic", "Empty = chosen automatically", "Blank = <value>" |
| Hint under Weight with spool | "Leave empty for a full spool." | "Blank = full" |
| The filament presets built for Bambu Studio and Orca Slicer | "Slicer presets"; recording a product line's values is "Add a line to the Filament Catalog" | "profile", "Add profile" |
| An add kept on the device before its spools are added | "Draft" / "Drafts" | "Unfinished add", "Unfinished adds" |

Every text the app shows is in `strings.xml` (none in Kotlin), and test 7 checks the catalogue and both generated
files against each other.

## 13. iPhone specifics of the web app

The web app is used mostly in Safari on iPhone and from the home screen (foundations section 3).

**Head of the page**, in this order (the colour values shown are Console's; the Hub fills in its default theme's,
section 15):

```html
<meta charset="utf-8">
<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">
<meta name="color-scheme" content="light dark">
<meta name="theme-color" content="#ffffff" media="(prefers-color-scheme: light)">
<meta name="theme-color" content="#11171c" media="(prefers-color-scheme: dark)">
<meta name="apple-mobile-web-app-title" content="Spoolwarden">
<meta name="apple-mobile-web-app-status-bar-style" content="default">
<link rel="manifest" href="manifest-light.webmanifest">
<link rel="apple-touch-icon" href="icon-180.png">
<script src="theme-init.js"></script>
<link rel="stylesheet" href="tokens.css">
<link rel="stylesheet" href="components.css">
<script src="strings.js" defer></script>
<script src="app.js" defer></script>
```

| Topic | Rule |
|---|---|
| Safe areas | `viewport-fit=cover`. The top bar adds `env(safe-area-inset-top)` to its top padding; the bottom bar adds `env(safe-area-inset-bottom)` to its height; sheets add it to their bottom padding; the rail and the content gutters use `max(var(--s4), env(safe-area-inset-left))` and the same on the right, so landscape keeps clear of the notch. The content's bottom padding is `calc(var(--tab) + env(safe-area-inset-bottom) + var(--s4))` so nothing hides behind the bottom bar; toasts and the job panel sit above it. |
| 16 px inputs | At or below 600 px every `input`, `select` and `textarea` uses `--fs-l` (16 px at the default text size). Smaller text makes Safari zoom the page when the field gets focus. Zoom is never disabled: no `maximum-scale`, no `user-scalable=no`. |
| Text size | `html { -webkit-text-size-adjust: 100%; }` so turning the phone does not enlarge text on its own; all sizes in `rem` follow the person's text-size setting. |
| Full heights | Sheets and the side drawer use `100dvh` (with `100vh` before it as a fallback), so Safari's toolbars never cover their bottom. |
| Keyboard | While a text field has focus at phone width, the bottom bar (the `nav` block at phone width, `02-components.md` 2.4) is hidden (`@media (max-width: 600px) { :root:has(input:focus, textarea:focus, select:focus) .nav { display: none } }`), so it does not ride above the keyboard. |
| Field hints | `inputmode="decimal"` for grams and temperatures, `inputmode="numeric"` for codes; `autocapitalize="off"`, `autocorrect="off"` and `spellcheck="false"` for addresses, codes and keys; `enterkeyhint` names what Return does. |
| Hover | Hover colours are written inside `@media (hover: hover)`, so a tapped button does not stay in its hover colour on a touch screen. `touch-action: manipulation` on controls removes the double-tap delay. |
| Long-press | iPhone has no hover tooltips: an icon-only button relies on its `aria-label`; the exact time behind a relative date (foundations section 2) shows on press-and-hold in a small popover. |
| Photos | `<input type="file" accept="image/*" capture="environment">` for one photo from the camera; `multiple` without `capture` to choose several from the library. |
| Status-bar colour | The two `theme-color` metas carry the light and dark `--surface` of the Hub's default theme, so the first paint is right. The page script then sets the `content` of both metas to the computed value of `--surface` at load, after every appearance or theme change, and when `matchMedia("(prefers-color-scheme: dark)")` changes. An explicit Light or Dark choice and a non-default theme therefore colour Safari's bar too. |
| Status-bar style | `apple-mobile-web-app-status-bar-style` is `default`: the system keeps its own bar and draws dark or light text for it. `black-translucent` is not used because it forces white status text, which cannot be read on a light theme. Check on a device: install the web app to the home screen, choose Light, Dark and System in turn with the phone in light and in dark mode, and confirm the status bar's text is readable each time. Where iOS keeps a bar that does not match `--surface`, that is the accepted difference of section 14. |
| Home-screen manifest | Two manifests, `manifest-light.webmanifest` and `manifest-dark.webmanifest`, with the same `name` and `short_name` "Spoolwarden", `display: standalone`, `start_url` (the web app's own address) and icons (one 180 × 180 and one 512 × 512). The light one has `theme_color` the default theme's light `--surface` and `background_color` its light `--bg`; the dark one the dark values (foundations section 5). The page head links the light one; the appearance script points the `<link rel="manifest">` at the manifest of the active appearance at load and whenever the active appearance changes (an explicit choice, or the system setting while System is chosen), so the browser offers to install the matching one. |

## 14. Accepted differences

What cannot be identical, and is accepted. Everything not listed here is the same on both platforms, and a
difference not listed is a defect.

| Topic | Web | Android | Why accepted |
|---|---|---|---|
| System font | The device's own: San Francisco on iPhone and Mac, Segoe UI on Windows, Roboto in browsers on Android | Roboto, or the phone maker's system font | By design: system fonts only, nothing downloaded (foundations sections 1 and 4.2). Sizes, weights and line heights are equal. |
| Odd weights (650) | Shown at 650 where the font is variable, else the nearest weight | The same rule | The system font decides |
| Palette's rounded stack | `ui-rounded` and the stack of foundations section 6.3 | `FontFamily.Default` | Android has no system rounded font; downloading one is not allowed |
| Monospace font | `ui-monospace` stack | `FontFamily.Monospace` | System fonts only. Tabular figures on both. |
| Back | The browser's back follows the address (`#printers/<id>`) | System Back (gesture or button) and predictive back (`android:enableOnBackInvokedCallback="true"`): it first closes the topmost menu, tooltip, dialog, sheet or drawer; then returns to the previous place, the same places the web address records; at a bottom-bar destination other than the first it goes to the first; at the first it leaves the app. With unsaved edits it asks first (foundations principle 4). | Each platform's own back control |
| Breadcrumb | Shown above the page title | An Up button in the top bar named "Back to <parent>" | The Android top bar is where people look for it |
| Pickers | Native `<select>` (a wheel on iPhone), the photo sheet of `<input type="file">`, the Web Share sheet where the browser offers it, else a download | `SwMenu`, CameraX in the app and the system photo picker, the Android share sheet | Each platform's own picker is the one people know |
| Touch and hover feedback | Hover `--surface-2`, pressed `--surface-3` on devices with a pointer | The platform's press ripple, coloured from the content colour | Native feedback. States that last (selected, current, expanded) use the same tokens on both. |
| Minimum touch size | 44 px | 48 dp for controls, tappable rows and menu items; icon buttons are 48 dp | Each platform's guideline (foundations principle 7). Visible heights of buttons and segmented controls are equal (`--ctl`). |
| Switch | 40 × 24 px track | Material `Switch`, 52 × 32 dp | Material's switch geometry; the colours and the On/Off word are the same |
| Window class edges | Phone up to 600 px, Tablet 601 to 1024 px, Desktop above | Material's classes: compact below 600 dp, medium to 839 dp, expanded from 840 dp | Foundations section 7 pairs Phone, Tablet and Desktop with these classes. A window from 840 to 1024 wide is Desktop in the app and Tablet in a browser. |
| Text field height | `--ctl`, label above the field | Material's `OutlinedTextField` height with the floating label inside the outline | `OutlinedTextField` cannot be shorter and still hold its label; colours, shape, hint and error lines are the same |
| Collection row height | At least `--row` | At least `ListItem`'s own minimum height | `ListItem` carries the row layout and semantics; dividers, type and colours are the same |
| Navigation indicator | Soft ground across the item, 3 px mark at the edge | Material's indicator pill in `accentSoft` behind the icon; the 3 dp mark is drawn on the rail item | `NavigationRail` and `NavigationBar` draw their own indicator shape |
| Shadows | CSS `box-shadow` values from `tokens.json` | Platform elevation shadow at the proposed `elevation.android` depth (section 3.4) | Android's light model draws its own shadow. The 1 px ring of `e2` is identical. |
| Tooltips | On hover and keyboard focus | On long-press | No hover on phones |
| Focus ring | `:focus-visible` | Drawn only for keyboard focus | Same intent; Android reports the input mode instead of a focus-visible state |
| iPhone status bar in the installed web app | As section 13 | Not applicable | iOS controls that bar |
| First frame on Android 10 and 11 | Not applicable | The empty window before the app draws follows the phone's light or dark setting | `setApplicationNightMode` exists from Android 12 |
| Very large text | Grows with the browser's text size | Android 14 and newer scale large sizes less than small ones (non-linear font scaling) | The system's text-scaling rule |
| Skip link | Present | None | Android screen readers move by headings and controls |
